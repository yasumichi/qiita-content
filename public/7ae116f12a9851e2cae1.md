# プロンプト1: fedora linux における名前解決の仕組み 

Fedora Linux における名前解決（ドメイン名から IP アドレスへの変換など）は、主に **`systemd-resolved`** が中心となって動作しています。

全体のフローと各コンポーネントの役割、設定の確認方法について解説します。

:::note info
筆者が検証した事項をノートで書いていきます。

Fedora Linux としていますが、Redhat や Ubuntu など著名なディストリビューションで採用されています。
:::

## 名前解決の全体フロー

アプリケーション（Web ブラウザや `curl` コマンドなど）が通信を行う際、以下の順序で名前解決が行われます。

```
[ アプリケーション ]
         │
         ▼
[ C ライブラリ (glibc: getaddrinfo) ]
         │
         ├──① /etc/nsswitch.conf を確認
         │
         ├──② files (`/etc/hosts` を参照)
         │
         └──③ resolve / dns (`systemd-resolved` へ問合せ)
                     │
                     ├── Local Cache (キャッシュ確認)
                     ├── mDNS / LLMNR (ローカルネットワーク検索)
                     └── DNS Server (外部 DNS へ問い合わせ)
```

:::note info
getaddrinfo の主な使用目的は、ホスト名やサービス名から、ネットワーク通信に必要なIPアドレスやポート番号などの構造体（addrinfo）を取得すること（プロトコル非依存の名前解決）です。

getaddrinfo の実装は、glibc の [nss/getaddrinfo.c](https://sourceware.org/git/?p=glibc.git;a=blob;f=nss/getaddrinfo.c;h=45b7f728a1c6d2dbb0a01051ff81584a28624a25;hb=HEAD#l2290) で定義されています。

- [Man page of GETADDRINFO](https://linuxjm.sourceforge.io/html/LDP_man-pages/man3/getaddrinfo.3.html)(JM Project による日本語訳)
:::

## 主要なコンポーネントと役割

### 1. `nsswitch.conf` (Name Service Switch)

`glibc` がどの順番で名前解決のデータソースを参照するかを定義しているファイルです（`/etc/nsswitch.conf`）。

Fedora のデフォルトでは、`hosts:` 行が以下のように設定されています。

```text
hosts: files myhostname mdns4_minimal [NOTFOUND=return] resolve [!UNAVAIL=return] dns
```

* **`files`**: 最初に入力されたホスト名が `/etc/hosts` に記載されていないか確認します。
* **`myhostname`**: 自ホスト名（ローカルマシン自身）を解決します。
* **`mdns4_minimal`**: `.local` ドメインのマルチキャスト DNS 解決を試みます。
* **`resolve`**: `systemd-resolved` の D-Bus サービスに直接問い合わせを行います。
* **`dns`**: `resolve` モジュールが使えない場合のフォールバック（従来方式の `/etc/resolv.conf` 参照）です。

:::note info
Name Service Switch となっていますが、現在では、認証に関する優先順位なども管理されています。

- [Man page of NSSWITCH.CONF](https://linuxjm.sourceforge.io/html/LDP_man-pages/man5/nsswitch.conf.5.html)(JM Project による日本語訳)

また、`/etc/nsswitch.conf` というファイルは、[authselect](https://github.com/authselect/authselect) というパッケージに属しています。

authselect の man ページの翻訳は、[Fedora 翻訳プロジェクト](https://translate.fedoraproject.org/) で行われ、upstream に還元されているようです。

```
$ rpm -qf /etc/nsswitch.conf
authselect-libs-1.7.1-1.fc44.x86_64
```
:::

### 2. `systemd-resolved` (名前解決マネージャー)

Fedora 33 以降、標準で有効化されているネットワーク名前解決サービスです。

* **役割**: DNS キャッシュ、mDNS/LLMNR、DNS-over-TLS (DoT)、インターフェースごとの DNS 設定統合（Wi-Fi と VPN で別の DNS を使うなど）を管理します。
* **スタブリゾルバ (`127.0.0.53`)**: `systemd-resolved` はローカルアドレス `127.0.0.53:53` で待機しています。`/etc/resolv.conf` は通常、この `127.0.0.53` を指すシンボリックリンクになっています。

:::note info

若干、説明が怪しいですが、/etc/resolve.conf は、メモリ上に展開されている `/run/systemd/resolve/stub-resolv.conf` へのシンボリックリンクになっています。

```
$ ls -l /etc/resolv.conf
lrwxrwxrwx. 1 root root 39  3月 19  2026 /etc/resolv.conf -> ../run/systemd/resolve/stub-resolv.conf
```

また、このファイルの中でネームサーバーが、127.0.0.53 に設定されています。

```
# This is /run/systemd/resolve/stub-resolv.conf managed by man:systemd-resolved(8).
# Do not edit.
#
# This file might be symlinked as /etc/resolv.conf. If you're looking at
# /etc/resolv.conf and seeing this text, you have followed the symlink.
#
# This is a dynamic resolv.conf file for connecting local clients to the
# internal DNS stub resolver of systemd-resolved. This file lists all
# configured search domains.
#
# Run "resolvectl status" to see details about the uplink DNS servers
# currently in use.
#
# Third party programs should typically not access this file directly, but only
# through the symlink at /etc/resolv.conf. To manage man:resolv.conf(5) in a
# different way, replace this symlink by a static file or a different symlink.
#
# See man:systemd-resolved.service(8) for details about the supported modes of
# operation for /etc/resolv.conf.

nameserver 127.0.0.53
options edns0 trust-ad
search .
```

:::

:::note warn
`/run/systemd/resolve/stub-resolv.conf` のコメントにも書かれていますが、このファイルは、`systemd-resolved` により、管理されています。書き換えてはいけません。

古い名前解決の仕組みにしたい場合は、`systemd-resolved` の無効化、[NetworkManager](https://gitlab.freedesktop.org/NetworkManager/NetworkManager) を手動設定にした上でシンボリックリンクを削除し、新たに `/etc/resolve.conf` を作成する必要があります。
:::

### 3. NetworkManager (ネットワーク接続管理)

ネットワークの接続（DHCP、Wi-Fi、VPN など）状態が変わるたびに、取得した DNS サーバー情報を `systemd-resolved` に通知します。


## 設定の確認・操作コマンド

Fedora で現在の名前解決状態や参照している DNS サーバーを確認する場合は、従来の `cat /etc/resolv.conf` ではなく **`resolvectl`** コマンドを使用するのが最も確実です。

### 現在の DNS 設定と状態を確認する

```bash
resolvectl status
```

* 各ネットワークインターフェース（`eth0` や `wlan0` など）ごとに、現在適用されている DNS サーバーや検索ドメインが表示されます。

### ドメインの名前解決テストを行う

```bash
resolvectl query example.com
```

* `systemd-resolved` 経由で名前解決を行い、応答速度や解決された IP アドレス、使用されたプロトコル等を確認できます。

### DNS キャッシュの統計確認と消去

```bash
# キャッシュの統計（ヒット率など）を表示
resolvectl statistics

# ローカルの DNS キャッシュをクリア
resolvectl flush-caches
```

:::note info
一般ユーザーで実行すると認証を求められます。
:::

## 従来の仕組みとの違いまとめ

| 項目 | 従来の Linux 方式 | Fedora (systemd-resolved) |
| --- | --- | --- |
| **設定参照先** | `/etc/resolv.conf` を各アプリが直接参照 | `systemd-resolved` サービスが一括管理 |
| **DNS キャッシュ** | 標準ではキャッシュなし（`nscd` や `dnsmasq` が必要） | 標準でローカルキャッシュが有効 |
| **マルチインターフェース** | VPN 接続時などの DNS 優先度制御が困難 | インターフェースごとに柔軟な Routing/DNS 設定が可能 |

# プロンプト2: Avahi はどの部分を担っているのか?

Avahi（アヴァヒ）は、DNS サーバーがないローカルネットワーク（LAN 内）において、**「設定なし（Zero Configuration / Zeroconf）」で端末同士の検索や名前解決、サービスの自動発見（DNS-SD）を行う部分**を担っています。

Apple でいう「Bonjour」の Linux/Unix 実装に相当するコンポーネントです。

:::note info
- [avahi - mDNS/DNS-SD](https://avahi.org/)
- [Bonjour プロトコルに関するセキュリティ上の暗黙の前提条件 (開発者や管理者向け) - Apple サポート (日本)](https://support.apple.com/ja-jp/101889)
:::

## 1. Avahi の主な 2 つの機能

### ① `.local` ホスト名の名前解決 (mDNS)

DNS サーバーに登録されていない LAN 内の機器同士を、`hostname.local` という名前で相互に検索・IP アドレスに変換します。

* **動作例**: LAN 内の Raspberry Pi に `ssh pi@raspberrypi.local` で接続できるのは、Avahi（または mDNSResponder）が動いているためです。

### ② サービスの公開と自動発見 (DNS-SD)

名前解決だけでなく、「この端末で何のサービス（プリンター、ファイル共有、SSHなど）が動いているか」を LAN 内にアナウンスしたり、他端末のサービスを探したりします。

* **動作例**:
* ネットワークプリンターを繋ぐと、ドライバ設定なしで自動的に検出される。
* ファイルマネージャー（Nautilus など）を開くと、LAN 内の共有フォルダが自動一覧表示される。

## 2. systemd-resolved と Avahi の関係・使い分け

Fedora Linux において、`systemd-resolved` と `Avahi`（`avahi-daemon`）は一部機能（mDNS）が重なっていますが、役割の広さが異なります。

| 項目 | `systemd-resolved` | `Avahi` (`avahi-daemon`) |
| --- | --- | --- |
| **主な得意領域** | **全体の DNS 管理** （インターネット問い合わせ、キャッシュ等） | **ローカルネットワークのサービス発見** （Zeroconf / DNS-SD） |
| **`.local` の名前解決 (mDNS)** | **可能**（クライアント応答・解決ともに基本機能でサポート） | **可能**（伝統的な標準実装） |
| **サービス発見 (DNS-SD)** | 不可 | **可能**（CUPS プリンターや Samba、AirPlay などの検出） |
| **Fedora での扱い** | デフォルトで必須動作 | デフォルトで同梱。デスクトップ環境で広く利用 |

### ポート（UDP 5353）の競合について

mDNS は UDP ポート `5353` を使用します。
Fedora のデフォルト構成では、**mDNS の解決やレスポンスは Avahi が主導**し、`systemd-resolved` 側は Avahi とバッティングしないよう適切に連携（あるいは mDNS 機能の一部を Avahi に譲る設定）が行われています。

* **単に `.local` の名前解決だけが目的の場合**: `systemd-resolved` のみでも処理可能です。
* **プリンター検索やネットワークブラウジング（CUPS / GUI デスクトップ）を使う場合**: `Avahi` が必要不可欠となります。

:::note info
`resolvectl status` の結果で `-mDNS` という結果が出て入れば、`systemd-resolved` 側で mDNS が無効になっています。(有効な場合は、`+mDNS`)

```
$ resolvectl status
Global
         Protocols: LLMNR=resolve -mDNS -DNSOverTLS DNSSEC=no/unsupported
  resolv.conf mode: stub

Link 2 (enp0s20f0u1c2)
    Current Scopes: DNS LLMNR/IPv4 LLMNR/IPv6
         Protocols: +DefaultRoute LLMNR=resolve -mDNS -DNSOverTLS DNSSEC=no/unsupported
Current DNS Server: fe80::103c:5936:fbe9:1
       DNS Servers: 192.168.0.1 fe80::103c:5936:fbe9:1
     Default Route: yes
```
:::

## 3. `nsswitch.conf` における Avahi

先ほどの `/etc/nsswitch.conf` の設定で登場した `mdns4_minimal` という記述は、まさに Avahi の提供するライブラリ（`nss-mdns`）を参照する設定です。

```text
hosts: files myhostname mdns4_minimal [NOTFOUND=return] resolve [!UNAVAIL=return] dns
```

この順序により、`.local` で終わるドメイン名の問い合わせがあった場合、通常の DNS サーバーへ行く前に `mdns4_minimal`（Avahi）へ処理が渡され、LAN 内のマルチキャスト検索で迅速にアドレスが解決されます。
